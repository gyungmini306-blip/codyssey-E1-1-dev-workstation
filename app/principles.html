01 / BUILD → RUN → REQUEST

이 페이지가 뜨기까지

설명 모형

‘이미지’는 실행 파일과 설정의 묶음입니다. Dockerfile은 그 묶음을 만드는 설명서이고, 컨테이너는 그 이미지로 만든 실행 환경입니다.

  1. 1소스 + DockerfileHTML · NGINX 설정 · 제작 방법
  2. 2이미지실행 준비물을 묶은 결과
  3. 3컨테이너NGINX가 실행되는 환경
  4. 4브라우저8080번으로 요청 → HTML 응답
STEP 1 / 4

먼저 실행할 파일과 제작 방법을 준비합니다.

app/index.html은 보여줄 페이지, nginx.conf는 서버 설정, Dockerfile은 이미지 제작 방법입니다.

FROM nginx:stable-alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY app/ /usr/share/nginx/html/
왜 필요한가?

평가자가 같은 소스와 Dockerfile로 이미지를 만들어 정해진 명령으로 실행할 수 있게 합니다. GitHub에는 소스와 제작 방법을 저장합니다.

설명 모형

찾는 위치: /etc/os-release

아까 pwd가 /인 상태에서 cat etc/os-release가 성공한 이유입니다. 다른 위치에서 해당 상대 경로의 파일이 존재하는지는 따로 확인해야 합니다.

권한을 더하면 644와 755가 됩니다.

각 묶음에서 읽기 r = 4, 쓰기 w = 2, 실행 x = 1을 더합니다. 체크를 바꿔 보세요.

그룹

파일의 x는 프로그램 실행, 디렉토리의 x는 진입·경로 탐색 권한입니다. root는 많은 접근 검사를 우회할 수 있으므로 ‘권한이 바뀜’과 ‘접근이 거절됨’은 구분해서 관찰합니다.

직접 할 실습과 제출 증거

Ubuntu 컨테이너에서 파일과 디렉토리를 각각 만들고 권한 변경 전후 출력을 남깁니다. 아래는 실행 예시이며 완료 로그가 아닙니다.

mkdir -p /root/e1-1/practice
cd /root/e1-1/practice
touch memo.txt
chmod 600 memo.txt
chmod 700 .
ls -ld . memo.txt
chmod 644 memo.txt
chmod 755 .
ls -ld . memo.txt

추가로 생성·복사·이동·삭제·내용 확인·숨김 파일 조회를 실제로 수행하고 명령과 출력을 기록합니다.

03 / LIFECYCLE

종료와 삭제는 다릅니다.

설명 모형

빌드 → 실행 → 중지 → 삭제를 눌러 보세요. 컨테이너를 삭제해도 이미지가 남는지 관찰합니다.

실행 준비물

이미지

아직 만들지 않음

codyssey-workstation:3.0
→
실행 인스턴스

컨테이너

아직 생성하지 않음

모형 속 web

이미지 빌드부터 시작하세요. 실제 Docker 리소스는 변경되지 않습니다.

docker build -t codyssey-workstation:3.0 .
hello-world가 바로 종료된 이유

컨테이너의 주 프로세스가 끝나면 컨테이너도 종료됩니다. hello-world는 출력 후 종료해 docker ps -a에 Exited (0)로 남았습니다. NGINX는 요청을 기다리며 계속 실행됩니다.

attach / exec / exit는 어떻게 다를까?
  • docker attach: 기존 주 프로세스 입출력에 연결합니다. 그 주 프로세스인 Bash에서 exit하면 해당 컨테이너도 종료됩니다.
  • docker exec -it 이름 bash: 실행 중인 컨테이너 안에 새 Bash 프로세스를 만듭니다. 이 추가 Bash에서 exit해도 주 프로세스가 계속 실행 중이면 컨테이너는 유지됩니다.
  • 대화형 컨테이너에서 Ctrl+P, Ctrl+Q로 연결을 분리하면 컨테이너를 실행 상태로 둘 수 있습니다. Ctrl+C는 분리 명령이 아니며 연결된 프로세스에 영향을 줄 수 있습니다.

이 차이를 실제 컨테이너 상태와 함께 관찰한 로그가 필요합니다.

04 / REQUEST & RESPONSE

내 PC의 8080과 서버의 80을 연결합니다.

연결 설명 모형

브라우저와 컨테이너는 서로 다른 네트워크 공간을 사용합니다. 이 웹 서버의 NGINX는 컨테이너 안 80번에서 요청을 받습니다.

내 PC · 브라우저localhost:8080이 주소로 요청
→
Docker 포트 매핑8080 → 80요청을 컨테이너로 전달
→
컨테이너 · NGINX80번에서 대기HTML로 응답

모형의 예상: 서버의 80번에 연결되므로 요청이 도달할 수 있습니다.

docker run -d -p 127.0.0.1:8080:80 codyssey-workstation:3.0

위 선택은 설명용이며 실제 포트를 변경하지 않습니다. EXPOSE 80은 포트 정보를 문서화하며, 실제 호스트 연결은 -p로 설정합니다. 실제 접속에는 서버 실행과 호스트 포트 사용 가능 여부도 영향을 줍니다.

직접 할 실습과 제출 증거

포트 지정 실행 명령, curl 응답, 주소창의 포트와 페이지가 함께 보이는 브라우저 캡처를 남깁니다.

05 / STORAGE

파일 변경과 데이터 보존은 어떻게 다를까?

설명 모형

① 호스트 파일을 수정하면 페이지도 바뀔까?

COPY는 빌드할 때 파일을 이미지에 담습니다. 바인드 마운트는 지정한 호스트 폴더를 컨테이너에 연결합니다.

→
모형 속 브라우저 · 새 요청 시 내용안녕, E1-1!이미지에 복사해 둔 내용
COPY app/ /usr/share/nginx/html/

이 편집 칸은 실제 HTML 파일을 바꾸지 않습니다. 실제 바인드 마운트에서는 호스트 파일을 수정하고 브라우저를 새로고침해 확인합니다. 마운트한 경로의 기존 파일은 연결한 호스트 파일에 가려집니다.

② 컨테이너를 삭제해도 데이터가 남을까?

같은 내용을 컨테이너 내부와 이름 있는 볼륨에 각각 쓴 뒤 컨테이너 삭제·재생성을 비교해 보세요.

컨테이너의 쓰기 가능한 층

컨테이너 내부 파일

비어 있음컨테이너 존재
Docker가 별도로 관리

이름 있는 볼륨 /data

비어 있음컨테이너와 별도 수명

먼저 양쪽에 데이터를 써 보세요. 실제 컨테이너나 볼륨은 삭제하지 않습니다.

직접 할 실습과 제출 증거

바인드 마운트는 실행 명령과 호스트 변경 전후 응답을, 볼륨은 생성·연결·데이터 작성·컨테이너 삭제·재연결 후 동일 데이터를 기록합니다. 이 모형은 실제 검증 로그를 대신하지 않습니다.

# 개념 예시: 먼저 볼륨 생성, 컨테이너에 연결
docker volume create e1-1-data
docker run -d --name e1-1-volume --mount type=volume,src=e1-1-data,dst=/data ubuntu:24.04 sleep infinity
